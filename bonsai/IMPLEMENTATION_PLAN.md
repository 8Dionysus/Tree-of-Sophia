# План реализации полного ядра бонсая

Дата: 1 ноября 2026. Рабочая база: `main` → `3574eb128b89d9d43d4e67c80fd493de3b0dcea5`.

Уточнение порядка, 2 ноября: текущий результат — законченный бонсай для
осмотра Дионисом. Перенос его содержания в ToS отложен до этого осмотра и
отдельного решения Диониса. Готовность экспорта и испытание механики не
разрешают начинать перенос. Обычное продолжение работы над бонсаем не
возобновляет этот этап.

Бонсай становится полноценным мини-Древом: человек читает произведение, разбирает язык, исследует философские предметы и отношения, выполняет объяснимые вычисления, работает с агентом и сохраняет результат для дальнейшего роста. Все эти возможности действуют на небольшом, содержательно богатом корпусе. «Заратустра» остаётся главным произведением; Античность сохраняет свою библиотеку и служит вторым действующим потребителем общих механик.

Этот документ задаёт реализацию и порядок выполнения. Предметные принципы и уже утверждённое содержание остаются в [CORE.md](CORE.md), исходных модулях и владельцах ToS. При реализации обновляется соответствующий владелец, а здесь отмечаются завершённые пакеты и точные результаты. Один выполненный показательный маршрут открывает дальнейшую работу по всему плану.

Основную модель переключает Дионис. Планирование и стратегию ведёт основной агент; при воплощении GPT-6.1 Sol Max отвечает за весь результат, интеграцию и выпуск. Субагенты получают самостоятельные ограниченные задания и возвращают проверяемый результат.

## Результат всего этапа

Готовое ядро соединяет следующие способности:

1. Целостное чтение книги и возвращение к точному месту выбранного свидетеля.
2. Филологическое исследование словоупотребления, контекста, значения, истории слова и различий переводов.
3. Полноценные карточки предметов, утверждений, отношений и ходов мысли.
4. Прямые и обратные ссылки, сохраняющие предмет, версию и историю исследования.
5. Объяснимые операции над содержанием, типизированными связями, временными и пространственными сведениями.
6. Оригинальный, справочный и познавательный режимы с общим состоянием исследования.
7. Живой агентный цикл: вопрос → материал → действие → результат → содержательное рассмотрение → продолжение.
8. Рост исследования внутри бонсая и сохраняемый экспорт предметных результатов и методов. Перенос в ToS следует отдельным этапом после осмотра.
9. Сохранение всех прежних источников, прочтений, оценок, личных графов, заметок и маршрутов.

Масштаб ограничивается корпусом и числом глубоко проработанных случаев. Для каждой способности нужен законченный пользовательский путь. Богатство будущего мирового корпуса растёт на этом действующем основании.

## Рабочие решения

- Развивать существующий `bonsai/`, общий интерфейс `public-research`, читатель и native Rust владельцев. Каждую новую функцию помещать рядом с уже принадлежащей тому же владельцу ответственностью.
- Использовать одни предметы, ссылки и исследовательские действия во всех режимах и агентных маршрутах. Производные индексы строить из текущих модулей и их версий.
- Сохранять тёмное пространственное исследовательское окружение, существующие линзы, поворот, глубину, коллекцию и маршруты. Карточки, читалка и текстовое представление дают дополнительные способы работать с тем же предметом.
- Сначала доводить рабочий пользовательский ход, затем следующий. KISS означает минимальное достаточное изменение существующего владельца; Pareto задаёт порядок по влиянию на целый путь; DRY удерживает одно определение поведения.
- Технический сбой превращать в конкретную задачу восстановления. Исполнитель устанавливает причину, исправляет вход, маршрут или код, повторяет затронутое действие и продолжает пакет.
- Содержательную неопределённость выражать точно: несколько прочтений, границы реконструкции, открытый вопрос с исследованными основаниями. Объём выполненной работы определяет полнота исследования, а статус утверждения — его основания.

## Сохранение существующей работы

Перед изменениями Sol фиксирует исходный commit, состав затрагиваемых модулей и экспорт исследовательского состояния через существующие функции. Авторские изменения идут во входы сборки; производные обновляются их штатным сборщиком. Сохранённые материалы старых проходов продолжают служить историей.

| Поверхность | Сохраняемый адрес или механизм |
| --- | --- |
| Core | ID узлов, связей, цепочек, точные цитаты, `proposed`, `assessment`, исходные и исправленные формулировки; авторский `control.json` |
| Старые графы | `demo:*`, `core:*`, `material:*`, `atlas:*`; действующие predecessor fingerprints и `upgradePublicGraph` |
| Workspace | `localStorage: tos-research-workspace-v1`; существующий Rust владелец и compare-and-swap |
| Блокнот | IndexedDB `tos-public-research-v1`: `meta`, `notes`, `readings`, `preferences`; вопросы, история, позиции и агентные задания |
| Полка | IndexedDB `tos-research-shelf-v1`: адресные записи и коллекции; существующий аддитивный импорт |
| Графы и позиции | `tos.public-research.graph.v1.<profile>.<fingerprint>`, companion `.owners`, `tos.public-research.graph-positions.v1.<profile>` |
| Подборка и язык | Временная подборка `tos.public-research.source-basket.v1`; сохранённый язык `tos.public-research.locale.v1` |
| Ранние прочтения | `atlas-held.mjs`, прежние отношения и исторические источниковые записи сохраняют собственные адреса и область подтверждения |

Новые поля представления получают совместимые значения по умолчанию. Существенное изменение сохраняемой формы сопровождается явной миграцией, которая оставляет исходный пакет доступным и восстанавливает личные привязки. Сохранённый fingerprint выбирается существующим механизмом от нового совместимого состояния к более раннему.

Один восстановительный сценарий охватывает заметку с точной цитатой, тезис, возражение, личную связь и позицию графа: экспорт → новая версия → импорт/миграция → открытие тех же предметов. Он выполняется на отдельной исследовательской копии. Привычный пользовательский экземпляр сохраняет свои данные и настройки.

## Общий предмет и состояние исследования

Один производный исследовательский индекс связывает доступные узлы, связи, цепочки, утверждения, употребления и цитаты. Он строится при сборке библиотеки из существующих модулей. Индекс предоставляет поиск по ID, соседство, входящие ссылки, зависимости и материал карточки. Карта, справочник, познавательный режим и агент читают этот индекс.

Предметные данные остаются у своих владельцев. Индекс хранит адреса и необходимые проекции. Текстовые тела читатель получает через provider; содержательные поля карточек ссылаются на авторскую запись. Фильтр представления и набор данных вычисления задаются явно.

Состояние исследования объединяет:

- профиль бонсая и режим опыта;
- выбранный узел, отношение, утверждение или текстовое место;
- закреплённые карточки и их положения чтения;
- текущий вопрос и ревизию личного исследования;
- маршрут и шаг;
- линзу, фильтры, камеру и масштаб;
- точного свидетеля, диапазон, выделение и позицию читателя;
- язык интерфейса и выбранные языки чтения.

Это составная проекция уже существующих владельцев состояния. У каждого остаётся собственное сохранение; общий контроллер координирует переход и восстановление. Режим опыта (`original`, `reference`, `cognitive`) отделён от предметного `mode: philosophy|corpus` в текущем API, линзы и языкового переключателя «Оригинал» у цитаты.

Выбор новой карточки открывает её начало. Возврат по истории восстанавливает прежнюю прокрутку, выделение и контекст. Переключение режима сохраняет вопрос и предмет. Прямой URL открывает тот же предмет в указанном режиме; существующие URL читаются прежним способом.

## Карточки узлов

Сохраняются имеющиеся содержательные разделы. Общее оформление имеет три глубины: короткий предпросмотр, закреплённая карточка, развёрнутая работа рядом с текстом или вторым предметом.

Первый экран карточки содержит название и тип, формулу произведения с голосом, короткий тезис исследователя, вопрос, читаемое состояние исследования и действия «Читать», «Сопоставить», «Связи», «Продолжить исследование». Основной источник доступен здесь же. Длинный фрагмент раскрывается целиком в той же карточке или читателе.

| Блок | Содержимое и поведение |
| --- | --- |
| Суть | Формула, вопрос, тезис, ответ, основания, роль в книге. Совпадающая точная цитата показывается один раз с указанием, какие формулировки на неё опираются |
| Развитие | Возникновение, изменения по книге, цепочки с глаголами переходов, поздние места, изменяющие раннее прочтение |
| Измерения | Собственные аспекты предмета; вычислимые сравнения имеют отдельное действие с выбранным правилом |
| Связи | Входящие и исходящие отношения, содержательные глаголы, направление, краткое основание, переход к собственной карточке отношения |
| Свидетельства | Точные места, голоса, употребления, варианты текста и переводов, словарные статьи, межтекстовые основания |
| История | Предложенная формулировка, рассмотрение, исправление, контрпрочтение, текущий результат и авторы действий |
| Моя работа | Заметка, собственный тезис, возражение, ответ, выбранные основания, продолжение с агентом |

Предметные блоки соответствуют типу: фигура раскрывает голос, адресатов и появления; трактовка — вопрос, тезисы и аспекты; аргумент — шаги и роли посылок; словоупотребление — языковой разбор; произведение — состав и свидетелей; персона — биографические сведения и их основания. Поля «тезис» и «ответ» показывают свои функции даже при общем источнике.

На широком экране карточку можно расширить и закрепить рядом со второй. На узком сохраняются вопрос, действия и доступный возврат к карте. Клавиатура проходит те же действия; фокус возвращается к вызывавшему элементу. Текст, ссылки и подписи остаются читаемыми при обычном увеличении страницы.

## Карточки отношений

Отношение имеет стабильный адрес, собственное содержание и историю. Карточка начинается с `предмет → содержательный глагол → предмет`, типа, короткого объяснения и кнопок точных источников. Оба конца доступны сразу.

Далее раскрываются область и условия, основания каждого конца и самой связи, ход реконструкции, промежуточные шаги, альтернативы, возражения, авторство и результат рассмотрения. Глагол произведения сохраняется рядом с более общим типом реестра. Направление и смысл обратного перехода выражаются словами.

Переход в источник подсвечивает относящийся к связи диапазон. Карта выделяет оба конца и выбранную цепочку. Из отношения можно открыть использующие его рассуждения, исключить его в личном сравнении, предложить уточнение и увидеть последствия. Историческая формулировка остаётся открываемой по своей версии.

Тезис, образ, аргумент и связь получают действия, соответствующие своему предмету. Возражение может указывать на конкретный шаг или отношение. Альтернативные связи сохраняются отдельно вместе со своими основаниями.

## Система ссылок

Ссылки используют стабильный предметный адрес и, когда требуется воспроизведение, точную версию. Общий resolver возвращает цель, читаемое имя, происхождение, состояние разрешения и действие открытия. Он продолжает текущие `source-address`, reader references и material bindings.

| Адресуемая цель | Состав |
| --- | --- |
| Предмет | Существующий ID, вид предмета и его владелец; текущая запись и доступная история |
| Утверждение | Устойчивый ID внутри авторского предмета, версия формулировки, автор, область, основания и оценка |
| Текст | Work, witness/version, слой и его digest, упорядоченные TextUnit и диапазоны; существующий native reference сохраняется целиком |
| Соответствие | Точные адреса обеих сторон, версия выравнивания, вид соответствия и его оценка |
| Отношение или шаг | Его собственный ID, участники, тип, область и версия |
| Исследование или расчёт | Вопрос, входные адреса и версии, выбранная операция, параметры, результат и история |

Содержательным полям, которым требуется самостоятельная ссылка, присваиваются ID в авторском входе; порядок элементов массива остаётся вопросом представления. Новые ссылки связываются с прежними ID и URL через явные соответствия.

Reader references считают Unicode code points. Переход от старого бонсайного `s/e` или от отображённой современной орфографии проходит существующее соответствие к исходному тексту. Проверка цитаты подтверждает тот же диапазон и слова.

Поведение ссылки едино: предпросмотр → открыть рядом → закрепить → вернуться. Человек копирует библиографически понятную ссылку с точным локатором. В подробностях доступны свидетель, версия и история. Внешняя ссылка говорит, что открывает: фрагмент, полный текст, издание или каталог.

Обратный индекс показывает, какие формулировки, отношения, заметки и расчёты используют место. Исправление источника или утверждения помечает соответствующие зависимости для пересмотра; исходный результат остаётся воспроизводимым.

Воспроизведение обеспечивают сохранённые байты версии. Существующий immutable public-corpus snapshot расширяется необходимыми дескрипторами версий core и выравнивания. Перед выпуском изменений сборщик сохраняет предыдущие используемые снимки в долговечном каталоге артефактов по digest; manifest выпуска перечисляет текущий снимок и удерживаемые предшественники. Публикация копирует их в адресуемую по digest часть статического набора. Resolver выбирает точный snapshot из ссылки и передаёт `createPublicCorpusProvider` адрес его каталога как `baseUrl`. Provider читает `manifest.json`; P1 добавляет проверку digest самого manifest по удерживаемому дескриптору, затем использует существующие проверки digest его участников. История предмета разрешается через тот же снимок. Следующий выпуск сохраняет все уже опубликованные адреса удерживаемых версий; совпадающие байты переиспользуются по digest.

Личный расчёт хранит в notebook пакет воспроизведения: версию операции, параметры, точные ссылки и минимальные неизменяемые входные значения, полученный результат и объяснение. Агрегатный экспорт переносит этот пакет. Отсутствующий внешний снимок показывается как конкретная недоступная версия с её адресом и действием восстановления из сохранённого пакета. Для собственных опубликованных снимков полнота удержания входит в сборку и приёмку P8.

Смена свидетеля выполняется через запись соответствия. Основное действие «Читать» открывает исходного свидетеля; переход к другому изданию становится осознанным действием сравнения.

## Читалка и филологическая работа

DTA и Антоновский 1913 подключаются как версии существующего произведения через source packets и `access/public-corpus/selection.v1.json`. Их публичную доставку собирает действующий `tos-access public-corpus-build`; читатель продолжает использовать существующий provider. Текст, ID и сведения о правах берутся из сохранённых свидетелей и их происхождения. Gutenberg остаётся самостоятельной версией с прежними адресами.

Человек читает все доступные главы каждого свидетеля, переходит между главами, ищет, выделяет, сохраняет заметку, открывает параллель и возвращается к карточке. Пропуски издания Антоновского показаны как особенности этого свидетеля. Сопоставление допускает один-к-нескольким, несколько-к-одному и отсутствие соответствия; уровень уверенности относится к конкретному сопоставлению.

Филологическая панель раскрывает конкретное употребление: форма → лемма и морфологические варианты → синтаксическая роль → контекст → значения → история и этимология → варианты перевода → исследовательское утверждение. Словарные и исторические сведения имеют собственные ссылки и даты применимости.

Начальный содержательный набор выбирается из действующих маршрутов книги: `Bruder`, `schenken`, `Gold`, `Segen`, `untergehen`, `Wiederkunft` и связанные формы. Для каждого прорабатываются употребления, контекстные различия, словарные источники и выбранные переводы. Общие функции работают по всей книге; глубина анализа явно видна для каждого употребления.

Существующие DWDS/Morpheus, lexical index, morphology и usage-context маршруты поставляют свои результаты. Дополнение одного анализа сохраняет альтернативы. Авторские переводы, опубликованные переводы, модельные предложения и исторические варианты имеют читаемое происхождение.

## Содержательное ядро и шесть предметных доработок

Sol продолжает сохранённый разбор книги через существующие сборочные входы. Terra независимо читает места и проверяет новые формулировки. Содержательная правка сохраняет первоначальное предложение и результат рассмотрения.

Нужно завершить шесть открытых предметных задач из `CORE.md`:

1. **Фигура внутри произведения.** Дать source-qualified предмету явную область произведения и роль; различать его, исторического носителя имени и автора. Отразить это в существующих реестрах и source-description маршруте с сохранением нынешних ID и связей.
2. **Голос и атрибуция.** Адресовать первичную и вложенную речь, говорящего, адресата и носителя цитирования. Связь атрибуции получает собственный источник и совместимый тип.
3. **Отношения мест текста.** Выразить повтор, вариацию, ответ, контраст и перекличку через точные адреса обеих сторон и содержательное основание.
4. **Семейства глаголов.** Связать конкретный глагол с подходящим типом отношения по смыслу и области применения. Формулировка произведения сохраняется в карточке и цепочке.
5. **Употребления и мотивы.** Связать бонсайные появления с native Occurrence и имеющимся motif-proposal маршрутом, сохраняя полный заявленный набор сравниваемых мест.
6. **Смысловые группы употреблений.** Разобрать употребление в контексте; голосовой режим становится одним из признаков, а смысловая группировка получает самостоятельное основание.

Далее отделить тезисы, шаги вывода и возражения там, где они действительно выражены в материале. Использовать имеющиеся `thought-description` и `thought-relation` контракты. Для проверочного логического случая подключить уже существующий JGB §21; его предметные различия сохраняются при показе рядом с «Заратустрой».

Все 28 предложенных узлов получают полный разбор: собственное раскрытие, связь с существующим предметом или сохранённое исследовательское предложение с содержательным результатом рассмотрения. По каждому видно, какие места прочитаны и что установлено. Маршруты братьев и дара, благословения, пастуха и Заратустры доводятся до целостного чтения.

| --- | --- | --- |
| Раздельная поддержка утверждения | Одна точная формулировка `p`, её версия и scope; явно классифицированные множества `E+` за `p` и `E−` за отрицание именно `p`. Сводка `β(p) = (E+ ≠ ∅, E− ≠ ∅)` сохраняет ссылки на каждый элемент | Пустые множества → «сведений нет»; только `E+` → «есть поддержка»; только `E−` → «есть опровержение»; оба → «есть поддержка и опровержение». | Различие явно заданных прочтений JGB §21 | Четыре бинарных признака прочтения: критика causa sui; признание критики несвободной воли; приписывание автору положительного учения о несвободе; утверждение исторической замены одного учения другим. `1` — признак явно включён; `0` — явно отсутствует в данном профиле; `null` — ещё не размечен. Все веса равны 1. `dH` — число различающихся координат, `d2 = √dH` | Профили `[1,1,0,0]` и `[1,0,1,0]` дают `dH=2`, `d2=√2`; `[1,0,0,0]` отличается от каждого на 1. Результат показывает различающиеся обязательства прочтений. При `null` возвращает список недостающих разметок; разные версии осей требуют явного соответствия |

Точный исследовательский вход для двух последних строк — [«Ручные смысловые пространства: точные данные и ожидаемые ответы v0.3»](https://chatgpt.com/space/page_60deadafaf7881919ab03e6682369765), профиль `jgb21-reading-features@0.1-proposed`, файл SHA-256 `74fbbeaa32ec014f38a484a9d9b5a7d30f6163162abee3f22093b0c7676ebeac`. Это предложенная ручная разметка. P5 сохраняет её происхождение и проводит содержательную проверку по точному свидетелю перед показом исследовательского результата. [Первая часть математического исследования](https://chatgpt.com/space/page_8969e9febc1c8191b44194c6222f4d4f) и раздел «Полярность утверждений ToS» второй части задают границу signed evidence и FOUR/FDE.

Первый реальный случай поддержки — [JGB §21, квалифицированная инверсия](../ToS/source-witnesses/relations/jgb21-conception-inversion/source-claims.jsonl). Его положительное основание поддерживает ограниченное сравнение `p`. Контрпрочтение в той же записи направлено на более сильное `q` — будто Ницше принимает механистическую несвободу. Оператор сохраняет две формулировки: поддержка `p` и ограничение `q` попадают в разные адресные записи. Заполнение `counterevidence_refs` само по себе сохраняет роль источника; знак для отрицания точного `p` устанавливается содержательным разбором. Один и тот же локатор сохраняет одну источниковую идентичность во всех ролях.

Остальные операции таблицы продолжают существующие поиск, пути, сравнение, временные и географические функции. Для каждого результата открываются входы, версия правила и смысл его применения. Реконструкция философского рассуждения сохраняет свой текст и основания рядом с формализацией.

В первой правке расчётов объединить atlas/core/personal состав в выбранной проекции. Счётчик различает число посещённых узлов и число переходов; главы и временные сведения рассчитываются только по доступным привязкам. Отдельно показывается число элементов без такой привязки.

## Три режима

В общей верхней навигации появляются «Оригинальный», «Справочный», «Познавательный». Это представления одной работы. Переключатель цитаты «Оригинал» остаётся языковым действием внутри источника.

| Режим | Пользовательская работа | Общий результат |
| --- | --- | --- |
| Оригинальный | Пространство, линзы, карточки, целая книга, сравнение, собственные мысли и агент | Полная исследовательская среда |
| Справочный | Структурированная статья о выбранном предмете, аргументы, хронология, источники, входящие/исходящие отношения, поиск и переходы | Читаемое текстовое представление тех же предметов и утверждений |
| Познавательный | Живой диалог и действия с подключённым ИИ, обратная связь, подсказки, самостоятельные связи и открытие следующего исследовательского хода | Личный опыт познания с сохранёнными основаниями и возможностью продолжить обычное исследование |

Справочник строится из тех же блоков содержания и resolver, располагая их в документном потоке. Ссылки ведут в тот же читатель и карточки. Редактирование личной мысли и работа с источником доступны из обоих представлений.

Познавательный режим хранит три различимых состояния: материал Древа; опыт человека, подтверждённый его действиями; материал, раскрытый в текущем сценарии. Уровень помощи задаёт педагогический ход:

- **Лёгкий:** агент активно связывает уже найденное, предлагает ближайший ход и помогает развить собственную находку.
- **Средний:** агент сочетает помощь с восстановлением оснований, проверками внимания и закреплением.
- **Тяжёлый:** человек самостоятельно восстанавливает основные связи, а агент отвечает на действия и точечные запросы.

Успешное действие — содержательное различение, обоснованная связь, найденный контрпример, исправление или новый вопрос. Альтернативное прочтение получает рассмотрение по основаниям. Человек выбирает уровень помощи и свободно возвращается в другие режимы с той же работой.

## Живой агент и познавательная сессия

Первая полная версия использует подключённого агента Codex через WebMCP. Модель и её исполнение принадлежат агентному хосту; Бонсай предоставляет точный контекст и действия. Такое подключение поддерживает реальное исследование без ручного обмена JSON. Существующий экспорт задания остаётся полезным форматом переноса.

В `public-research/app.mjs` подключить существующие `PageCommandRegistry`, Rust/WASM rules и `createWebMCPAdapter`. Текущий публичный вход их ещё не регистрирует. Контекст страницы включает выбранный предмет, точные источники, вопрос, режим опыта, ревизию workspace и доступные операции.

Переиспользовать команды чтения контекста, выбора, раскрытия, исследования, сравнения и staging. Добавить только необходимые действия для сессии: прочитать очередь событий человека; показать адресную подсказку/вопрос; предложить следующий ход; представить результат вычисления; завершить шаг с объяснением. Ответ агента связан с session/event ID и ревизиями предметов.

Сессия работает так:

1. Человек открывает познавательный режим, выбирает вопрос и помощь, подключает агента к странице.
2. Агент получает контекст и событие, читает основания через те же операции, при необходимости открывает дополнительное место.
3. Агент возвращает вопрос, подсказку или предложение действия в панель Бонсая с точными ссылками.
4. Человек читает, выбирает, формулирует мысль или связь; действие добавляет следующее событие.
5. Агент оценивает содержимое действия, объясняет обратную связь и продолжает маршрут.
6. Исследовательский результат сохраняется в действующем workspace; предложение общего изменения проходит существующий source/review маршрут.

Конкретный хост первой версии — активная задача Codex с Browser Use и WebMCP. Кнопка «Подключить агента» показывает готовое задание с URL, session ID и выбранным вопросом; человек один раз запускает его в Codex. Основной хост открывает видимую человеку IAB-вкладку (`visible: true`), обнаруживает WebMCP, присоединяется к session ID и остаётся в цикле сопровождения до остановки человеком. Пользователь продолжает работу в этой видимой вкладке; её DOM, IndexedDB и очередь принадлежат тому же документу, который обслуживает основной агент. При переходе из другого browser profile существующий workspace переносится штатным экспортом/импортом, а активная сессия начинается в выбранной общей вкладке.

P0 проверяет доступность этой видимой поверхности человеку и управление тем же документом основным Codex: совпадают URL, выбранный предмет и результат действия в UI. Если browser-привязка требует восстановления, Sol исправляет её на этом раннем шаге и повторяет тот же проход. Первое изменение P6 подключает реестр и выполняет один полный обмен «действие UI → событие → инструмент → видимый ответ»; далее на нём строится педагогический цикл. Для автоматического испытания Terra открывает отдельную фоновую вкладку и выполняет обе стороны сценария. Её результат проверяет механику; выпуск также проходит основной хост в видимой пользовательской вкладке.

В существующий реестр команд добавляются действия сессии: `join`, `next-event`, `respond`, `pause` и `resume`. `next-event` получает session ID и последний подтверждённый event ID, ожидает до 20 секунд и возвращает событие либо пустой результат ожидания. Активная задача Codex повторяет чтение; `respond` связывает видимую карточку ответа с event ID и ревизией вопроса. Следующий пользовательский клик обслуживается той же задачей. Готовая инструкция хосту хранится рядом с `agent-bridge`, используется кнопкой подключения и описывает этот цикл, отмену и возобновление.

Очередь и последний подтверждённый ID сохраняются в существующем notebook. Состояния UI: «ожидает подключения», «агент подключён», «обрабатывает действие», «пауза», «требуется переподключение». Последний обмен обновляет отметку подключения; после 60 секунд без обмена страница показывает возобновление. Перезагрузка сохраняет session ID и неподтверждённые события. Активный хост повторно выбирает вкладку, обновляет список WebMCP, выполняет `resume` и продолжает с подтверждённого ID. Если задача Codex уже завершилась, действие «Продолжить с агентом» даёт готовое задание для её повторного запуска с тем же session ID; запущенная задача выполняет `resume` и забирает сохранённую очередь.

При изменении вопроса или источника ответ сохраняется с прежней привязкой, агент получает актуальный контекст и пересчитывает следующий ход. Повторная доставка одного события распознаётся по ID. Переключение режима приостанавливает педагогическое представление, сохраняя исследование и возможность продолжения.

Личная адаптация, улучшение метода и обучение моделей имеют свои результаты. Согласие на использование личных материалов для общей библиотеки и обучения оформляется отдельным пользовательским действием, как предусмотрено замыслом режимов.

## Рост и перенос

Перенос в ToS в этом разделе описывает следующий этап. До осмотра бонсая
и отдельного решения Диониса source-owner запись, рассмотрение и admission
содержания не выполняются. Пробный перенос на изолированной копии остановлен;
его результаты сохранены отдельно и не означают принятия содержания Древом.

`lib/export.mjs` расширяется на философские предметы, утверждения, основания, атрибуцию, употребления и рассмотрение. Существующие исторические records/claims и их формы сохраняются. `identities.json` связывает бонсайные ID с native ToS предметами. В переносимом пакете сохраняются версия формата, commit и digest входов, таблица соответствия ID, предметные records, отдельные Claims, точные источники, формы и история рассмотрения.

Конкретный приём использует [source-owner front door](../mechanics/growth-cycle/parts/branch-growth-cycle/docs/SOURCE_COMMAND_DISCOVERY.md): `tos-native-owner-command source-commands --discover`, затем выбранный `source-commands --invocation`. Предметы идут через `public-profile-create` / `source.create` с профилями `entity-types.v1.json`; отношения с адресными концами — через `public-claim-create-v1` / `claims.create` и `source_claim_profile` своего предиката. Схемы тезиса, аргумента, шага и возражения — [thought-description](../ToS/contracts/thought-description-record.schema.json); их связей — [thought-relation](../ToS/contracts/thought-relation-claim.schema.json). Сохранённые JGB §21 source-create packages дают рабочие примеры этих форм. Источниковые Text/Alignment bindings продолжают свои native маршруты.

Недостающая часть P7 — преобразование бонсайного пакета в последовательность этих owner-запросов. Оно добавляется рядом с существующим экспортом и branch-growth consumer: сначала зависимости и отсутствующие предметы, затем Claims и формы. Один входной ID получает одно явное соответствие; повторный запуск использует те же command IDs и проверенные receipt. Имеющийся предмет читается по своей версии; изменение проходит его revision route. P4 завершает нужные предметные профили, поэтому consumer получает конкретные схемы и отношения. Содержательные предложения сохраняются как предложения в source records/Claims; source-visible assessment и scoped admission выполняются отдельными шагами того же прохода.

Передача проверяется на самостоятельной выбранной копии данных ToS с её owner-конфигурацией. Минимальный сквозной пакет содержит предмет, тезис, отношение, точный источник и запись рассмотрения. Consumer проводит подготовку, запись и рассмотрение; native access читает полученные предмет, отношение и источник. Проекция возвращает ту же связь в интерфейс. Затем этим же маршрутом переносится остальной подготовленный философский пакет. Канонический статус остаётся результатом соответствующего решения владельца.

Для роста метода выбрать один исследовательский эпизод: вопрос, доступные основания, предложенные варианты, проверка, изменение результата и выделенный приём. Применить приём к новому фрагменту, затем к подходящему фрагменту другой книги из существующего корпуса. Сохранить, что перенеслось и что потребовало изменения. Метод переносит способ исследования; предметы новой книги раскрываются по её тексту.

Sol передаёт Luna задания с конечным набором файлов, точными полями и ожидаемой формой ответа. Философское решение и архитектурный выбор принимает основной исполнитель с содержательной проверкой. Terra получает достаточно контекста для самостоятельного результата, включая рабочий URL и конкретный пользовательский вопрос.

Обычная рабочая группа: Sol, одна Terra и одна Luna. Вторая Terra полезна для независимого содержательного чтения одновременно с браузерной проверкой. Число агентов растёт вместе с независимыми готовыми задачами.

При явном выборе модели использовать доступную обвязку с `fork_turns: "none"` и полным ограниченным заданием. Пример параметров призыва:

```json
{"task_name":"bonsai_ui_check","model":"gpt-6.1-terra","reasoning_effort":"xhigh","fork_turns":"none","message":"Конкретное задание и входы"}
```

Задание содержит цель, точные пути и revision/URL, собственную область изменений, исходные предметные правила, ожидаемый рабочий результат, необходимую проверку и форму возврата. Возврат содержит результат, изменённые файлы или наблюдаемый UI, основания, выполненную проверку и конкретный следующий шаг. Sol читает результат, проверяет существенное и интегрирует его; ответственность остаётся у Sol.

Официальные основания распределения: [модели Codex](https://learn.chatgpt.com/docs/models#recommended-models), [субагенты](https://learn.chatgpt.com/docs/agent-configuration/subagents), [Sol](https://developers.openai.com/api/docs/models/gpt-6.1-sol), [Terra](https://developers.openai.com/api/docs/models/gpt-6.1-terra), [Luna](https://developers.openai.com/api/docs/models/gpt-6-luna). Выбранные уровни усилия заданы Дионисом; практический состав команды определён задачами проекта.

## Browser Use у Terra

В этой сессии Terra действительно открыла узел, отношение, точную цитату, читатель и ветвь Античности. Дополнительная свежая Terra успешно открыла собственную IAB-вкладку и получила текущий ответ WebMCP: `No WebMCP tools are available in this document.` Это исходное состояние для P6.

Проверенный порядок:

1. В первом вызове `mcp__cua_repl` выполнить ровно документированный вход, например `await cua.createBrowserTab('iab', url, {visible:false});`, и прочитать возвращённую документацию.
2. Работать в собственной вкладке агента. Номера вкладок родителя принадлежат другой браузерной сессии. Для subagent IAB применяется фоновая вкладка.
3. Получить свежий UI, выполнить реальные клики, чтение и ввод по сценарию, проверить результат визуально и по доступному состоянию.
4. Для WebMCP получить capability `webmcp`, вызвать `fetchTools()`, прочитать `description()` и выполнить действительно зарегистрированную команду. После смены документа или регистрации обновить список.
5. При потере браузерной привязки получить свежий `cua.getState`, восстановить собственную вкладку документированным способом. В этой сессии пустой browser inventory у продолженного агента исправлен свежим призывом Terra с тем же заданием и собственной вкладкой; Browser Use и обнаружение WebMCP после этого выполнены.
6. Sol сохраняет незавершённый сценарий, передаёт восстановленному агенту точный шаг и получает результат действия. При необходимости Sol сам локализует сбой, пока идёт независимая работа следующего пакета.

Для проверки живого агента требуется настоящий вызов инструмента страницы и видимый ответ в Бонсае. Для интерактивной проверки требуется действие в браузере. HTTP, чтение кода и автоматические тесты дополняют эти результаты своими областями.

## Проверки по делу

Разработка использует существующее покрытие. Постоянный тест добавляется для конкретного важного поведения, которое иначе останется без защиты. Его место — существующая проверка соответствующего владельца. Разовые инвентаризации, диагностические скрипты и обзорные сравнения сохраняются как рабочие результаты вне постоянного набора тестов.

| Изменение | Минимальная содержательная проверка |
| --- | --- |
| Адреса, диапазоны и версии | Существующие source-address/reference/fragment tests; один сквозной случай исходного свидетеля с выделением и возвратом |
| Сохранение и миграция | Существующие graph-transfer, notebook, shelf и workspace checks; восстановительный браузерный проход на копии |
| Карточки, справочник, локализация | Terra проходит изменённый сценарий, узкий экран и клавиатуру; необходимые существующие web/type проверки |
| Философское содержание | Citation/core check плюс независимое чтение источника и контрпрочтения; контрольные случаи `control.json` |
| Оператор | Объявленный вход и ожидаемый содержательный результат в существующих query/measure проверках; показ объяснения в UI |
| Агентная сессия | Существующие page-command/WebMCP/agent-bridge проверки расширяются на контекст и доставку; живой browser цикл с повтором события и изменением вопроса |
| Экспорт | Существующий bonsai check и native round trip выбранного философского пакета |
| Выпуск | Селектор и необходимые lanes из [RELEASING.md](../docs/RELEASING.md), затем опубликованные пользовательские маршруты |

После достаточного подтверждения пакет идёт дальше. Повторная проверка связана с новой правкой, выявленным дефектом или изменившейся зависимостью. Полный набор необходимых CI проверок выполняется на целостном кандидате; успешный результат того же неизменённого кандидата переиспользуется по release route.

Рекомендация OpenAI также прямо предусматривает соразмерное тестирование и завершение после достаточной проверки: [Testing and verification](https://developers.openai.com/api/docs/guides/latest-model#testing-and-verification).
